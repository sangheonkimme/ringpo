검증일 2026-10-22. 운영 배포·마이그레이션·실제 Meta/메일 발송 없음.

- 확정 rate 거부에만 기존 job의 추가 시도 한 묶음을 부여한다. 사람 의도/멱등 키/기존 시도 기록/기한/계정 pause와 budget은 보존한다. unknown·sending·accepted·late accepted·영구 실패를 거부한다.
- 최근 1시간 계정별 실제 결과·오류 코드, 큐/알림/리포트 지연을 화면에 표시한다. 확인 필요/만료/기한 임박 알림은 계정·종류·UTC 날짜별 영속 outbox로 중복 억제한다.
- 관련 통합 3개 파일 **24개 통과 (28.13초)**. 소유권/OFF/기한/요청 재사용, 동시 재처리, 추가 횟수 소진, pause 보존, 원장 일치, outbox/메일 fixture와 0013 empty up/down/up 포함.
- 타입 검사 5.24초, lint 11.25초, Next build 27.95초, worker build 0.91초 통과.
- 프로덕션 standalone 모바일 390×844에서 운영 지표·실패 작업을 확인하고 실제 Server Action으로 재처리를 예약했다. 계정 일시정지 유지, 재처리 버튼 제거, JS 오류 0/가로 넘침 없음. 실제 sender는 정지하고 외부 네트워크는 차단했다. 최초 브라우저 검사는 화면 refresh 완료 전에 버튼 수를 읽어 실패했으며, DB에서 retry/allowance=5/attempts 유지가 확인됐다. refresh 완료를 기다리도록 시험을 수정한 뒤 통과했다.
- [운영 화면](m2-5-operations.png), [재처리 뒤 화면](m2-5-retry.png), [브라우저 결과](m2-5-browser.json).

최종 전체 회귀는 **82개 파일/524개 통과, 실제 10분 부하 1개 opt-in skip** (358.35초)했다. 이후 추가한 3,000건 단일 계정·재처리 allowance 보존 시험과 확장 혼합 부하도 아래 별도 실행에서 통과했다. `GONGGU_RUNTIME_M2=1`은 기존 실제 10분/250계정/댓글 3,000건 시험에 FAQ 250개와 주기적인 성과 리포트 조회, 운영 지표/알림 수집을 추가한다. 외부 Meta API는 로컬 HTTP fixture로 대체한다.

## 재현

기존 통합 테스트 global setup은 대상 DB의 스키마를 초기화한다. 아래 `TEST_DATABASE_URL`에는 **별도로 만든 테스트 DB만** 지정한다. 동시에 두 Vitest 프로세스를 같은 DB에 연결하지 않는다.

```bash
# 실제 10분 유입 + 오픈 발송 + FAQ/리포트/운영 지표
GONGGU_RUNTIME_LOAD=1 GONGGU_RUNTIME_M2=1 \
GONGGU_RUNTIME_LOAD_REPORT=/tmp/gonggu-mixed.json \
pnpm exec vitest run --project integration tests/integration/campaign-runtime-load.test.ts

# 첫 progress 로그 뒤, 같은 시험 DB에 읽기 전용 예상 시각 관측기 실행
GONGGU_RUNTIME_LOAD=1 GONGGU_FORECAST_OBSERVER_PREFIX=/tmp/gonggu-forecast \
pnpm exec tsx scripts/gonggu/observe-load-forecast.ts

# 위 시험이 끝난 뒤: 한 계정 3,000건, 가상 시각 7.5시간 및 미시작 lease 복구
GONGGU_SINGLE_ACCOUNT_LOAD=1 GONGGU_SINGLE_ACCOUNT_REPORT=/tmp/gonggu-single.json \
pnpm exec vitest run --project integration tests/integration/campaign-dispatch-load.test.ts -t 'never exceeds'
```

관측기는 오픈 15초 전에 대기 12건이 모두 확보된 계정 20개(최소 10개)를 선택한다. 계정이 60개 미만이거나 대상 대기열이 충분하지 않으면 실패한다. 테스트 본체 PG pool 10 외에 관측용 pool 최대 2개가 사용된다. 예상 시각을 저장한 후 같은 캠페인의 확인된 private reply 완료 시각과 비교한다.

## 첫 확장 부하 실행의 실패와 수정

[첫 실행 기록](m2-5-first-load-failure.json)은 **실패**로 남긴다. 기존 자동화 250건의 초기 private reply는 78.339초, 공개 답글은 188.571초에 모두 수락됐지만, 테스트의 후속 답장 생성기가 180초까지만 기다려 중단됐다. 댓글 3,000건은 영속화됐으나 전체 송신 완료를 검사하기 전에 teardown했으므로 이 실행을 누락·중복 0의 근거로 사용하지 않는다.

후속 답장 생성기의 대기를 300초로 조정하고 실측 대기 시간을 결과 JSON에 추가했다. 모든 백그라운드 작업의 실패를 즉시 포착하고, 실패 시 FAQ 예약 시험도 즉시 정리하도록 고쳤다. 제품의 전송 한도·재시도·worker 수를 바꿔 시험을 통과시키지 않았다. 수정한 harness는 타입/lint를 다시 통과했고 전체 10분 혼합 부하를 새 DB 상태에서 다시 실행하여 통과했다.

## 단일 계정 3,000건과 최종 롤백 검사 — 통과

[단일 계정 측정 JSON](m2-5-single-account.json). 가상 시각으로 3,000건을 동일 계정/채널에 넣고 미시작 lease 하나를 61초 뒤 복구한 후 전부 발송했다. 기한 우선 순서, 고유 댓글 3,000개, 전체 작업 sent, **누락 0·중복 0·어느 rolling hour에서도 최대 400회**를 확인했다. 복구 이후 가상 경과 시간은 **7시간 30분 8.250초**, 단순 3,000÷400 예상은 7시간 30분이었다. 실제 7.5시간을 기다린 soak 시험은 아니다.

최초 확대 시험은 가상 시계가 claim/dispatch 동안 고정되어, rolling guard의 2초 경계에서 수천 개 대기 작업을 같은 시각으로 반복 확인했다. 1,200건 수락을 관측한 시점 이후 시험 시간 예산이 소진되기 전에 중단했다([기록](m2-5-single-clock-note.json)). 실제 worker처럼 각 round의 처리 소요 시간이 흐르도록 가상 시계를 수정했다. 시간당 원장 guard와 제품 코드는 변경하지 않았다.

이 helper를 쓰는 두 부하 시험을 모두 다시 실행했다. 250계정 3,000건 85.041초, 한 계정 3,000건 237.706초에 통과했다. 0013 empty up/down/up과 사용된 재처리 allowance가 있으면 down을 거부하는 검사까지 **2개 파일/4개 시험, 330.53초 통과**했다. 수정한 시험/관측 스크립트의 타입·lint도 통과했다. 제품 코드의 전체 524개 회귀 및 Next/worker build 결과는 앞 절과 같다.

## 남은 외부 출시 조건

코드·로컬 fixture·부하·브라우저 검증과 PR 작성은 완료했다. 실제 Meta 테스트 계정 두 개로 동의/IGSID/private reply/팔로우와 셀러 echo를 확인하는 작업은 미실시다. 운영 식별자의 장기 보존 Q14도 제품 정책 확인이 필요하다. 기본 feature flag OFF와 FAQ 계정 readiness OFF를 유지하며, 운영 배포/마이그레이션은 수행하지 않았다. [출시 점검](../02-release-checklist.md), [운영 절차](../runbook.md).
