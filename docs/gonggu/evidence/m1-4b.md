# M1-4b 기존 자동화의 공통 발송 예산 검증

확인일: 2026-10-21 UTC. 기존 matcher/요금·중복 예약/DM 본문은 재사용하고 Graph write에만 공통 PG budget·시도 원장·lease 검사를 연결했다. 운영 배포와 실제 Meta 호출은 하지 않았다. 메시지 수신/팔로우 후속 응답과 캠페인 송신 루프는 M1-4c에서 연결하기 전까지 운영 cohort를 활성화하지 않는다.

## 검증한 불변식

- 한번도 활성화하지 않은 flag-OFF 계정은 기존 공개 답글/DM/플랜/링크 경로를 사용한다. 신규 예산/발송 원장/댓글 timestamp 조회를 만들지 않는다.
- 같은 계정의 공구 sender와 기존 자동화를 실제 DB·fixture Meta로 함께 실행해 private reply 호출 간 9초 이상의 공통 간격을 확인했다. 별도 allowance를 만들지 않는다.
- 공개 답글 budget이 더 느려도 가능한 DM은 먼저 보낸다. 다음 처리에서는 공개 답글만 재개하고 DM을 반복하지 않는다.
- 외부 수락과 comment event의 sent/message ID를 같은 transaction에 기록한다. local pipeline 상태만 유실시켜도 acceptance 원장을 보고 복구한다.
- 요청 응답 유실/5xx는 `send_unknown`으로 종료하고 사람 중복 예약과 usage를 유지한다. 새 claim epoch가 생긴 뒤 이전 worker의 늦은 성공은 `late_result`에만 남고 자동 재전송하지 않는다.
- 형식 fallback은 명확한 4xx `100/2534015` 거부에만 적용한다. text로 바꾼 뒤 다음 budget 기회에 보낸다. 5xx에 같은 subcode가 포함돼도 fallback하지 않는다.
- source lease는 refund되는 attempts와 별개인 단조 증가 `send_lease_version`으로 확인한다. 예약/해제/상태 변경은 같은 source 행 잠금 안에서 처리한다. 네트워크 호출 동안 DB transaction을 잡지 않는다.
- 기존 만료 scheduler와 worker claim도 같은 행 잠금으로 경쟁한다. 수락된 DM 예약을 만료 처리로 되돌리지 않으며, 팔로우 요청이 이미 나간 경우 응답 대기를 유지한다.
- private reply deadline은 Meta의 댓글 작성 시각을 확인한다. 읽기 실패는 쓰기 결과 불명과 구분하며 Retry-After/usage header를 계정 cooldown에 반영한다.
- 플래그 OFF 뒤 마지막 공통 write+한 시간+permit 여유까지 같은 예산을 유지한다. 이 구간의 write는 안전 구간을 연장한다. 한 시간 이상 발송이 없어 기존 경로로 돌아간 뒤 ON하면 그 사이 untracked legacy 발송이 있었는지 확인해 warmup한다. 캠페인이 재활성화 후 첫 sender인 경우와 permit 직전 경합도 검증한다.

## 시험 범위

전체 **55개 파일/363개 테스트**를 통과했다(320.65초). 이후 unknown을 별도 통계로 표시하는 회귀를 추가해 관련 3개 파일/24개 테스트를 통과했고, 만료 scheduler의 claim 경합/팔로우 수락 예약 보존 사례를 추가해 해당 8개 테스트를 통과했다. 현재 테스트 수는 366개다. 타입 검사/lint/worker 빌드/Next 프로덕션 빌드도 통과했다.

[250계정·3,000건 발송 결과](m1-4b-virtual.json): 가상 시계와 지연 100ms의 로컬 HTTP fixture, PG pool 10/HTTP 동시성 64에서 수락 3,000건, 누락·중복·unknown 각각 0건이었다. 실제 경과 91.737초, 가상 발송 완료 102초다. 이 시험의 계정당 호출은 12건이므로 시간당 경계는 별도의 단일 계정 401건 rolling-window 시험으로 검증한다. 실제 Meta 요청은 0건이다.

동일 계정 혼합 사례는 예산 공유를 검증하며 250계정 전체 서비스 throughput을 의미하지 않는다. [M1-3 실제 시계 6,000작업 결과](m1-3.md)와 달리 이번 전체 회귀의 기본 부하 시험은 가상 시계를 사용한다. 최종 메시지 수신·renderer·metadata·기존 자동화를 합친 실제 시계 부하는 M1-4c 이후 다시 검증한다.

## 롤백과 남은 검증

`0006` up/down/up과 transition 이력 보유 시 down 거부를 검증한다. 이미 공통 예산으로 보낸 계정은 flag OFF만으로 구 worker를 즉시 되돌리면 안 된다. 호환 adapter를 유지하고 최근 발송 원장이 한 시간 창에서 사라진 뒤에만 완전한 구 경로 복귀를 고려한다. 구/신 worker를 동시에 띄우는 rollout은 허용하지 않는다.

팔로우 안내는 검증된 사용자 응답을 받는 text 경로를 준비했으며 일반 postback만으로 프로필 동의/24시간 창을 열었다고 간주하지 않는다. 실제 두 Meta 계정 검증과 팔로우 후속 수신 연결 전 운영 활성화는 보류한다. 추가 OAuth 권한은 없다.
