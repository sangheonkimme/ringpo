# M1-4c 메시지 수신과 팔로우 후속 처리

확인일: 2026-10-21 UTC. 기존 GraphClient, DM job/발송 원장, 공통 계정 budget, 참가자별 delivery 제약을 확장했다. 신규 Redis/외부 queue는 없다. 이 PR은 수신·분류 모듈이며 실제 webhook/worker 연결과 기존 `fg:` 일반 DM adapter는 M1-4d에서 함께 연결한다. **운영 활성화·실제 Meta 발송은 하지 않았다.**

## 확인하는 동작

- 공식 Instagram messaging envelope만 해석한다. 수신 계정과 sender/recipient 관계를 검증하고, self/위조 echo/mid 누락을 제외한다. 큰 ID를 문자열로 보존한다.
- 같은 메시지가 3회 동시에 들어와도 inbox는 한 행이다. 처리 중 재시작은 lease/version으로 복구하며 늦은 profile 조회 결과로 새 잡을 만들 수 없다.
- 창과 동의의 근거는 Meta `messaging.timestamp`의 실제 사용자 메시지다. webhook 수신 시각, 미래 시각, echo, 삭제, 일반 postback만으로 창을 만들지 않는다. 역순 도착으로 창을 되돌리지 않는다.
- 삭제 tombstone을 보존해 원문이 나중에 도착해도 복원하지 않으며, 삭제된 메시지를 근거로 대기 링크를 보내지 않는다.
- 신규 댓글에는 먼저 직접 답장을 요청한다. 이미 검증된 동의가 있고 follower=true라면 최초 private reply로 구매 링크를 보낸다. 일반 DM 창이 없는 사용자에게 일반 DM을 보내는 우회는 없다.
- 명시적 `팔로우했어요` 응답/검증 가능한 action만 처리한다. 계정·예상 수신자가 일치해야 하며 여러 캠페인/legacy gate가 모호하면 추측하지 않는다. 임의의 부정 응답은 팔로우 완료로 해석하지 않는다.
- 비팔로워 reminder 1회, link 1회를 기존 delivery 제약으로 보장한다. 동시 응답과 webhook 재전송에서도 일반 DM 잡은 하나다.
- 프로필 필드 누락은 unknown이다. 동의 후 network/5xx 장애만 셀러의 fail-open 설정 대상이며, rate/권한/토큰 오류는 링크 발송으로 우회하지 않는다. Retry-After와 계정 cooldown을 읽기에도 적용한다.
- 일반 DM은 현재 대화 창, 원래 source 메시지의 deadline, 삭제 여부를 발송 직전에 다시 검사한다. 새로운 대화가 열려도 오래된 source 잡을 소급해 되살리지 않는다.
- `0007`은 additive migration이다. 비어 있을 때 up/down/up을 지원하고 수신/조회 이력이 있으면 down을 거부한다. 계정 삭제 시 inbox/대화 상태도 cascade 삭제한다.

## 검증 결과

전체 **59개 파일/415개 테스트**를 통과했다(383.25초). 타입 검사/lint/worker 빌드/Next 프로덕션 빌드도 통과했다. 부하 fixture의 예약 DM 계정에 Pro 권한을 명시해 실제 dispatch 권한 검사를 거치게 했다. 권한을 제거한 계정의 예약 DM이 보류되는 회귀도 포함한다.

[250계정·3,000건 발송 회귀 결과](m1-4c-virtual.json): 가상 시계, 100ms 로컬 HTTP 지연, PG pool 10/HTTP 동시성 64에서 수락 3,000건, 누락·중복·unknown 0건. 실제 경과 114.825초, 가상 완료 102초다. 계정당 12건이므로 시간당 경계는 별도 401건 rolling-window 시험으로 확인했다. 실제 Meta 호출 0건이다. 이 시험은 발송 엔진만 측정하며 메시지 수신·기존 sender·대시보드를 합친 실시간 서비스 부하는 M1-4d 이후 검증한다.

운영 웹/워커/DB 컨테이너는 모두 실행 중이며 재시작 횟수 0, strict health는 HTTP 200 (`db=true`, `worker=true`)이었다. 운영 DB/설정/배포 변경은 없었다. 각 테스트는 격리한 로컬 PostgreSQL과 모의 API만 사용한다. UI 변경은 없으며 버튼/quick reply의 실제 Meta 지원과 실계정 두 개의 동의·팔로우 흐름은 아직 검증하지 않았다.

## 권한과 남은 연결

추가 OAuth 권한은 없다. 확인 근거는 [설계의 Meta 공식 문서 표 M3 User Profile API, M7 Messaging API, M8 Webhook Fields](../01-design.md)와 캐시한 2026-10-21 공식 문서다. 기존 `instagram_business_basic`, `instagram_business_manage_messages` 범위의 메시지/프로필 read를 사용한다. `message_echoes` capability/실계정 동작 확인과 FAQ의 셀러 직접 응답 중단은 후속 단계다.

M1-4d 전에는 새 수신 모듈을 운영 webhook에 붙이거나 캠페인 송신 루프를 켜지 않는다. 기존 팔로우 후속 일반 DM까지 같은 budget/확인 필요 정책을 거쳐야 전체 계정 한도를 보장할 수 있다.
